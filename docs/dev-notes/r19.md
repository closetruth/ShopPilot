## 2026-11-02 · Task 2 注册表与权限

### 关键产出

- `app/tools.py` 拆包为 `app/tools/`：`context.py`（AgentContext）、
  `permission.py`（Caller/Denied/authorize）、`registry.py`（ToolSpec +
  Registry + `@registered`）、`builtin.py`（四个内置工具）、`__init__.py`
  导出 `agent_tools()` / `tool_labels()`
- `agent.py`、`context_builder.py`、`customer.py` 改吃注册表
- `tests/test_tool_registry.py`：注册/重名/覆盖/白名单过滤/authorize 矩阵/
  destructive 注册即报错/模型可见 schema 不含 runtime

### 我拒绝或纠偏了什么

- `NoArgs` 空入参模型没塞进 registry，而是放进 `app/schemas.py`：入参模型
  本来就归那里管，注册中心只管元数据

### 翻车与返工

- **spike 只覆盖了一半**。回显工具的 schema 没开 `extra="forbid"`，
  真实工具（ProductQuery 等）全开着，`runtime` 会被 pydantic 判成多余字段；
  同时空入参 schema 会命中 LangChain 的「无字段直接返回空 kwargs」短路，
  runtime 一起丢。修法是 `RegisteredTool` 子类：先把注入参数摘出来校验
  干净参数，再把注入参数合回去。这一条说明 spike 必须用真实 schema 复验

## 2026-11-02 · Task 3 审计表与仓储

### 关键产出

- `tool_audit_logs`：三索引（工具+时间、访客+时间、状态+时间）
- `app/repo/audit.py`：`record` / `list_logs` / `mask_args` / `digest`
- 脱敏是键名白名单式（`phone|mobile|address|real_name|id_card|email` → `***`），
  不做正则猜内容：猜内容会漏，也会误伤订单号这类业务标识
- `error` 只留「异常类型 + 首行」，避免堆栈把 TEXT 列塞爆
- `store.py` 加 `record_tool_audit` / `list_tool_audits` / `mask_audit_args`

### 我拒绝或纠偏了什么

- 没有把 `result` 全量落库：审计要能回答问题「谁在什么时候用工具做了什么」，
  不需要复现完整返回体，全量落库只会让表迅速膨胀

### 翻车与返工

- 无。`test_write_failure_does_not_raise` 用 monkeypatch 换掉 `connect`，
  确认审计链路断了也不影响工具返回

## 2026-11-02 · Task 4 执行引擎

### 关键产出

- `app/tools/executor.py`：`Executor.invoke` 一条链路走完
  校验 → 鉴权 → 预览 → 执行 → 审计，五个结局都只有一行审计
- 包装工具 `build_tool` 现在直接转给 executor，`registry.py` 里的
  `_dispatch` / `call_impl` 删除；`validation_error` 也搬到 executor
- `runtime_meta` 把「取会话号、取访客」从 invoke 里拆出来，单独可测
- 超时用 `asyncio.wait_for` 包住 `to_thread`，同步 impl 不会卡事件循环

### 我拒绝或纠偏了什么

- 审计里的 `caller` 暂时写死 `"agent"`：现在只有 ToolNode 这一条入口。
  confirm/cancel 进来时再传参，不提前抽象

### 翻车与返工

- 并发用例最初断言墙钟时间 < 0.35s，被审计写库的固定开销带偏（实测
  两次 sleep(0.2) 合计 0.46s）。改成在 impl 内部记录执行区间、断言区间
  重叠——测的是「有没有并发」，不该把数据库延迟算进去
- 校验用例最初拿 `Args`（默认 `extra=ignore`）传多余字段，pydantic 直接
  忽略，断言不到 `wrong_field`。改成两条：缺必填字段 + `extra="forbid"`
  下拒多余字段，后者才是内置工具的真实配置

## 2026-11-02 · Task 5 待确认动作

### 关键产出

- `pending_actions` 表 + `app/repo/pending.py`（create/get/resolve/
  list_by_visitor，30 分钟过期）
- `Executor.invoke` 遇到 `requires_confirmation` 不再执行 impl，改为
  `_suspend` 落一条 pending 并返回 `pending_action`；`confirm` 用库里存的
  `args_json` 重放，`cancel` 只置终态
- 工具定义新增两个可选钩子：`preview`（挂起前的只读检查，返回
  `ok=False` 就不出卡片）与 `summarize`（生成卡片内容）
- `draft_work_order` → `create_work_order`，`requires_confirmation=True`；
  订单归属与重复建单的检查整体前移到 `preview`，执行体只剩「真建单」
- `agent.py` prompt 同步改写：卡片生成 ≠ 已提交

### 我拒绝或纠偏了什么

- `pending_actions` 没有复用 `work_order_drafts`：后者是「顾客手填、
  只针对工单」的专用表，前者要装任意工具的任意参数。两张表并行，
  Task 9 再在 README 说明双轨关系
- `confirm` 失败（如数据库抖动）**不**把动作置终态，允许顾客再点一次；
  失败已经进审计，置终态反而会让一次临时故障变成永久失败

### 翻车与返工

- 预览逻辑最初写在工具实现里（原 `draft_work_order` 直接返回
  `created: False`）。挂起语义引入后这条路径会先建卡片再报错，
  必须把检查前移到 `preview`，执行体才干净
- 前端卡片原来读 `draft.order_no / issue_type / description` 固定字段，
  通用化后改为读 `summary.fields`；工单号前缀是 `WO` 不是 `WO-`，
  测试断言跟着改

## 2026-11-02 · Task 6 SSE 与对话页接线

### 关键产出

  让手填能力消失，不在本轮范围内

### 翻车与返工
