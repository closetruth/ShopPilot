# r21 实测记录

## 远端算力现状（开工探测）

本机探测结果：

| 项 | 结果 |
|---|---|
| `192.168.6.23:22` | 开放，但只支持密码认证（`Permission denied (publickey,password)`） |
| `192.168.6.23:3306` | 开放，MySQL 8.4 在远端 docker 里（`.env` 的 `MYSQL_HOST/PORT` 指向它） |
| `192.168.6.23:19530` | 开放，Milvus |
| `192.168.6.23:9091` | 开放，Milvus metrics |
| `192.168.6.23:3005` | 未开放（Langfuse 未在跑，与 r20 的可选依赖定位一致） |
| `192.168.6.23:3307` | 未开放（那是本机 compose 暴露的端口，远端不适用） |
| `192.168.6.23:8010` | 未开放（训练服务端口空闲，可用） |
| `192.168.6.23:2375/2376` | 未开放，没有 Docker TCP API |
| 本机 docker | 守护进程未启动，`docker context` 只有 desktop-linux 且连不上 |

结论与处置：

1. **拿不到 GPU 型号**。SSH 只支持密码，没有免密通道，无法非交互探测
   `nvidia-smi`。因此训练容器做成**运行时自适应**：`server.py` 启动时探
   `torch.cuda.is_available()`，有卡走 `fp16 + batch 16`，无卡走
   `fp32 + batch 8`；
   `deploy/trainer-compose.yml` 默认不声明 GPU，另给
   `deploy/trainer-gpu.yml` 覆盖文件，远端确认有卡后
   `docker compose -f trainer-compose.yml -f trainer-gpu.yml up -d`。
   这样不必等算力结论就能把链路做完。
2. **`8010` 未被占用但可能被防火墙拦**。端口做成 `TRAINER_PORT` 可配，
   并在本机脚本里加「连不上就提示 SSH 隧道」的分支
   （`ssh -L 8010:127.0.0.1:8010`），不把失败写成 500。
3. **MySQL 与 Milvus 都在远端**，本机没有 docker 依赖，所以数据流水线
   与仓储测试可以直接跑，不受训练容器进度影响。

## 训练数据放哪：结论是放远端

一开始数据集是本地构建后 `docker cp` 进容器的。核对端口探测结果时发现
这个设计是绕远路：**标注（`finetune_labels`）、FAQ、轨迹三份数据本来就
在 192.168.6.23 的 MySQL 里**，本地构建等于先拉一遍再传回去，多一次往返，
还多一个「忘了同步」的失败模式——训练跑在旧标签上，指标好看但模型是错的。

所以改成：`POST /datasets/build` 在容器内直连 MySQL 现取标注重建
train/dev/test，本地接口只负责编排与登记，不再跑第二份构建逻辑。

代价是训练镜像的构建上下文从 `deploy/trainer` 改成仓库根，需要把 `app/`
取数层（只依赖 pymysql 与几个纯函数模块）和 `scripts/finetune_dataset.py`
拷进去，配 `.dockerignore` 排掉数据文件与虚拟环境。取数链路不碰检索与
LLM，所以不会把 torch 之外的东西拖进镜像。

唯一仍走本地的是 `candidates.jsonl`：算它要 embedding 接口 + Milvus 召回，
且内容是静态快照（候选不随标注变化），用命名卷 `trainer-candidates`
一次性放进去即可。缺失时只是少了 hard negative，训练照跑。

## 待远端确认的两条命令

在远端机器上执行后把输出贴回来，即可把 Task 0 补全：

```bash
nvidia-smi --query-gpu=name,memory.total --format=csv
docker info --format '{{.NCPU}} {{.MemTotal}} {{.ServerVersion}}'
```

在此之前，容器按 CPU 默认配置推进，不影响后续任务。

## 发布门禁：三把尺为什么缺一不可

单看任何一把都会被糊弄过去：

| 尺 | 量什么 | 单看它会漏掉什么 |
|---|---|---|
| 离线 test | 金标在**全池**里排第一 / 前三的比例 | 只说明拟合了这批标注，换个问法就未必 |
| 低置信度回放 | 低置信度池里有多少被救回来 | 才是「飞轮攒的东西有没有变成能力」 |
| 端到端回归 | `doc_hit_rate` 不比基线低 2 个点以上 | 防「离线涨了、线上没动」 |

门槛是 `HIT1_MIN=0.75` / `MRR3_MIN=0.80` / `REPLAY_MIN=0.25` /
`DOC_HIT_TOLERANCE=0.02`，判定写在 `app/finetune/gate.py` 的纯函数里，远端
`activate` 端点与本地测试共用同一份，避免出现「页面说达标、端点说不达标」。

三处刻意的收紧，都是为了不让门禁在错的方向上放行一次：

1. **字段缺失按未达标**。跳过等于放行「压根没评估」，而那正是最该拦的情况。
2. **回放只认 `low_conf_id` 不为空的标注**。r13 复用集与轨迹增强样本都没有
   这一列；若把全部标注算进来，这把尺就退化成 test 尺的第二次抽样。
3. **回放分母为 0 时提示「样本为 0」而不是「修复率 0%」**。前者该去补标注，
   后者该去调模型，混在一起只会让人去调参。

还有一个顺序问题：`activate` 必须**先判门禁再写 active 文件**。反过来的话
会出现「请求 409 被拒，但模型已经切过去了」——页面显示旧版本，线上跑新版本。

端到端那把尺只能在本地算（容器里没有对话图，Milvus Lite 数据文件又被运行中
的服务独占），所以走 `POST /api/admin/finetune/models/{v}/evaluate` 把两个
数字带进容器，不填就是「没跑」，门禁如实拦下。

## 远端实跑顺序

本机 docker 守护进程未启动、远端 SSH 只支持密码，所以构建与实跑要在远端手工执行：

```bash
# 1. 远端拉最新代码后构建（上下文是仓库根，不是 deploy/trainer）
docker compose -f deploy/trainer-compose.yml up -d --build

# 2. 检索快照只需放一次
docker cp data/finetune/candidates.jsonl shoppilot-trainer:/app/candidates/

# 3. 建数据集 → 训练 → 评估，三步都在容器内
curl -s -X POST localhost:8010/datasets/build -H 'Content-Type: application/json' -d '{"seed":20261104}'
curl -s -X POST localhost:8010/train -H 'Content-Type: application/json' -d '{}'
curl -s -X POST localhost:8010/models/<version>/evaluate -H 'Content-Type: application/json' -d '{"e2e":null}'
```

先不带 `e2e` 跑一次，看清离线两把尺的数字；端到端要另起本地 app 跑
`uv run python -m scripts.eval_pipeline` 拿到 `doc_hit_rate` 与基线，再填进
页面输入框重跑评估，门禁才会给出达标结论。
