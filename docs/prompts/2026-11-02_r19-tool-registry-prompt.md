## 本轮任务

做工具注册中心：参数校验、权限控制、执行引擎、审计留痕、MCP 接入、
建工单确认。

现在工具是写死在 `app/tools.py` 里的一个列表，加一个工具要改三处代码，
谁被调用了、传了什么参数、成功还是失败，全都没有记录。权限也没分层，
所有工具对所有人一视同仁。

这轮要把工具变成「注册出来的」：每个工具有名字、描述、参数模型、
数据范围、风险等级、可调用者白名单，集中登记，程序可读，页面可见。
所有调用走同一个执行引擎：先校验参数，再判权限，再执行，最后落审计。
建工单不能由模型直接写库，模型只能提出「待确认动作」，顾客点确认才落单。

MCP 也要接进来：外部工具通过 MCP 协议接进同一个注册中心，
走同一条执行链和同一份审计，不能另开一套。

## 验收标准

- `/admin/tools` 能看见全部注册工具与元数据
- 每次工具调用在审计表留一行，参数脱敏、结果摘要
- 模型提出建工单 → 顾客点确认 → 工单落库；点取消 → 不落单
- 越权确认（别人的 action）返回 404
- 非法参数返回结构化错误，不抛栈
- MCP 工具能调通，审计里 source=mcp
- MCP 配错不拖垮服务启动
- 全量测试绿 + 浏览器实跑

## 过程裁定

- **MCP 走客户端方向**（服务是消费方，接外部工具；不做对外暴露）
- **权限三层**：数据范围 scope（visitor / public / admin）×
  风险等级 risk（read / write / destructive）× 调用者白名单
  allowed_callers
- **建工单泛化为通用待确认动作**：`pending_actions` 表 + 确认/取消接口，
  前端只认 `summary.fields` 结构，不绑死业务字段
- **审计独立表** `tool_audit_logs`，不塞进现有 messages
- **注册中心用装饰器 + 进程内注册表**，不引外部插件框架
- **验收自带最小 stdio MCP server**，不依赖第三方服务
- **拦截方式先做 spike**：包装工具保留 `runtime` 签名 + 显式
  `args_schema`，若 `ToolRuntime` 注入不成立，退回「工具体内调 executor」
