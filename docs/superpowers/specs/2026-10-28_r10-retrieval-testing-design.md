# 检索链路测试与阈值标定

日期：2026-10-28
状态：已确认

## 问题

被问到「测试能查出 FAQ 里的知识吗」，检查后发现：**不能**。

现有 18 个与 FAQ 相关的用例里，没有一条验证真实数据能否被检索到：

| 已有测试 | 覆盖 | 缺口 |
|---|---|---|
| `test_faq_import.py` | frontmatter 解析、小节切分、ID 唯一 | 导入后能否被搜到 |
| `test_vector_store.py` | 临时假数据的存入与检索 | 真实 47 条 FAQ 的召回质量 |
| 无 | — | `search_knowledge` 工具本身 |

后果：如果 `search_knowledge` 里的 `store.faq_by_id()` 写错，或阈值定得失准，
测试仍全绿。这正是上一轮 `reindex.py` 崩溃却无人发现一事的同类问题。

## 新增测试

`tests/test_retrieval.py`，不造假数据，用 `data/faq` 导入的真实内容走
端到端链路（建索引 → 检索 → 回表 → 阈值过滤）。

| 用例 | 防的是什么 |
|---|---|
| 九类政策问题参数化 | 真实提问能否命中对应文档（退货/物流/发票/价保/退款/会员/投诉） |
| 返回内容逐字比对数据库 | 用的是 MySQL 原文，不是向量里的拼接文本 |
| 结果按分数降序 | 排序在应用层显式做 |
| 全部结果高于阈值 | 阈值过滤生效 |
| `top_k` 生效且被夹到 1–5 | 越界参数不传给 Milvus |
| 无关问题返回空（5 条样本） | 不硬凑结果 |
| 商品问题不命中政策 | 两类数据走不同工具 |
| 商品问题与阈值留有余量 | 分界线不被擦线通过 |

模块级 fixture 只建一次索引，避免每条用例都付一次嵌入 API 往返。

## 阈值标定

原值 `0.5` 是在没有任何真实数据时拍的。加入测试后立刻暴露问题：

> 「明天几点开会」得分 **0.521**，命中「发票开具时效」。

发票条款含「时效」概念，与「几点」语义沾边，属于阈值过松导致误召回。

实测 47 条 FAQ 的分数分布：

| 分组 | 样本数 | 分数区间 |
|---|---|---|
| 相关政策问题 | 14 | **0.630 – 0.729** |
| 无关问题 | 10 | 0.302 – **0.521** |
| 商品问题 | 1 | 0.466 |

分界在 0.521 与 0.630 之间。取 **0.58**，两侧各留约 0.05 余量。

调整后验证：

| 查询 | 结果 |
|---|---|
| 退货运费谁出 | 命中 P-RET-001，引用条款与 12 元上限 |
| 明天几点开会 | 被拒，回答「我是店铺客服，只能处理商品、订单和售后」 |
| 要投诉你们的服务（0.630） | 仍能命中，但回答转为追问细节而非硬套政策 |

## 阈值的维护

换嵌入模型、改嵌入文本模板、重建索引后都要重新标定。为避免下次
「改完没人发现」，测试承担守门职责：

- `test_irrelevant_queries_all_below_threshold`：5 条无关问题任一条漏网即失败
- `test_threshold_has_margin_on_product_queries`：商品问题距阈值不足 0.02 即失败

阈值本身就是产品决策，写死在代码里并附标定依据，比藏在配置里更容易被
后来者质疑和修正。
