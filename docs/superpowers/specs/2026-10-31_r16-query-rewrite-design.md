# ShopPilot 阶段十六设计：Query 标准化（售后口语改写）

## 意图

顾客不会用政策术语提问。「东西坏了想退」「快递好久没动」这类口语和
知识库里的「质量问题退货」「物流延迟」之间隔着一层语义鸿沟，纯向量
检索靠相似度硬扛：

实测（真实库，47 条 FAQ，BGE-M3）：

| 口语 query | 原分 | 拼术语后 | 现状 |
|---|---|---|---|
| 包装破了 | 0.553 | 0.643 | ❌ 被拒答闸挡掉 |
| 快递好久没动 | 0.619 | 0.771 | ❌ 被挡，改写后命中补偿标准 |
| 运费我不要出 | 0.645 | 0.729 | ❌ 压线被挡 |
| 赠品也要退回去吗 | 0.638 | 0.654 | ❌ 压线 |
| 东西坏了想退 | 0.675 | 0.727 | ✅ 过但分偏低 |
| 七天了还能退吗 | 0.748 | 0.826 | ✅ |

两条路都通向同样的条款，分数差 0.1-0.15——正好横跨 0.65 拒答闸。
这不是阈值能解决的（r14 已验证阈值两侧没有可靠分界线），是 query
本身的措辞问题。

## 目标

1. 知识检索前做一层**规则词表改写**：口语说法 → 政策术语，零 LLM 调用
2. 改写只作用于检索，不影响意图分类（分类看顾客原话）
3. 改写不比现状差：改写后检索仍证据不足时，用原话回退重查一次
4. 改写前后 query 落 agent_traces（数据飞轮延续，观测改写质量）

## 非目标

- 不做 LLM 改写兜底（改坏风险 + 延迟；先落词表方案看数据）
- 不动业务/投诉/闲聊路径
- 不改检索本身（纯向量 + 阈值维持 r13/r14 结论）
- 不做同义词挖掘工具（词表手工维护，规模小收益直接）

## 反目标

- 不允许改写让原本能命中的 query 变差（回退机制兜底）
- 不允许改写层消耗 LLM 调用
- 不允许把改写结果当意图分类输入（分类必须看原话——「投诉的流程
  是什么」改写成术语后会被误判）

## 架构

```
意图 = knowledge
   ↓
[Query 标准化]  纯函数：词表匹配，命中则拼接改写
   ↓            「快递好久没动」→「快递好久没动 物流延迟 停滞 补偿」
向量检索（改写后 query）
   ↓ 证据不足？
[回退]  原话再查一次，取两者中分高的一组
   ↓
置信度闸（0.65，不变）→ 生成回答
```

改写是**拼接不是替换**：保留顾客原话（嵌入信号），追加标准术语
（补召回信号）。替换会丢掉原话里的具体信息（比如「京东快递好几天
没动」里的「京东」）。

## 词表

`app/query_rewrite.py` 模块内嵌词表，键为口语触发词，值为追加术语。
来源是政策小节名（锚定真实条款）+ 实测增益验证：

| 触发词（正则） | 追加术语 |
|---|---|
| 坏了/有问题/有毛病/瑕疵/故障 | 质量问题 |
| 破了/破损/摔坏/压坏 | 运输破损 商品完好 |
| 不想要了/后悔了/拍错了 | 七天无理由退货 |
| 没动静/没更新/不动了/好久没到/太慢了 | 物流延迟 停滞 补偿 |
| 丢件/丢了/没收到货 | 丢件处理 理赔 |
| 退钱/退回来/把钱退了 | 退款金额与时效 |
| 运费谁承担/不想出运费 | 运费承担 |
| 换个/换一件/换货 | 换货与维修 |
| 开票/发票 | 发票开具条件 |
| 补差价/降价了/保价 | 差价计算 |
| 赠品 | 赠品 商品完好 |
| 投诉你们/给个说法 | 投诉处理原则 转人工 |

用户裁定：不为单条 query 硬调词条（「包装破了」改写后 0.643 仍差 0.007
过闸，为此继续调术语组合性价比不高）——词条按实测值收货，该条预期
改为「分数显著提升，仍可能拒答」。

维护规则：新增词条必须先跑 `tests/test_query_rewrite.py` 的增益验证
（原分 < 0.65 且改写后 ≥ 0.65，或改写后分数提升 ≥ 0.05），防词表
膨胀成噪声源。

**与 r14 冻结测试的关系（用户裁定：更新测试，接受新行为）**：
「要投诉你们的服务」现有测试冻结为必须拒答；「投诉你们」触发词改写后
它将越闸命中投诉处理条款。这是合理的改进——口语投诉措辞由知识路径
给出投诉处理原则 + 转人工指引，意图分流不变（规则先行仍判 complaint
的进模板，直接打检索端点的测试语义变化）。测试更新为新行为并注明
r16 裁定。

## 风险

- **改写把好 query 带偏**：拼接的术语可能把命中拉向错误条款（实测
  「运输破损 包装破损」纯术语反而掉分）。缓解：拼接不替换 + 回退
  取优 + 词表增益验证门槛
- **词表误伤**：触发词过宽（比如「有问题」命中「这个商品有什么问题
  吗」）。缓解：触发词用完整短语优先，单字词不加；增益测试盯住
  现有用例分数不降
- **术语过期**：政策文档更新后词表与条款名脱节。缓解：词表术语
  来自小节名，`test_query_rewrite` 校验术语在 FAQ 内容中出现

## 验收

1. 「包装破了」→ 检索分数从 0.553 显著提升（词条实测 0.643），命中
   正确小节；仍过不了闸则拒答属预期（用户裁定：不为单条硬调）
2. 「快递好久没动」→ 命中物流延迟补偿条款并给出回答（现状 0.619 被挡）
3. 现有 8 条检索测试全部通过、命中 doc 不变、分数不降（含触发词的
   4 条被改写，断言放宽为命中与阈值行为不变，不逐字比分数）
4. 「明天几点开会」等无关 query 仍被拒答（改写不误放无关问题）
5. agent_traces 的 detail 里能看到 rewritten_terms / rewritten_query /
   fallback_used（改写发生时有记录）
6. 全量测试通过

## 留给构建者的决定

- 词表正则的具体写法（词组优先、边界处理）
- 回退取优的比较口径（max_score 还是 results 数量）
- 测试里增益验证的参数化组织方式
