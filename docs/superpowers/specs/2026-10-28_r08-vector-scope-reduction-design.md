# 向量检索范围收敛

日期：2026-10-28
状态：已确认

## 决定

向量索引**只保留 FAQ 政策知识**。商品与工单改为纯结构化查询，不再进入
Milvus。

## 理由

### 工单：不需要，且有害

单个顾客的工单只有个位数，`list_my_orders` 一次就返回全部订单及其关联
工单。用语义搜索在几条记录里找，比直接枚举更慢、更不可靠。

更关键的是安全成本：工单是私有数据，放进向量索引就必须在检索层加
`visitor_id` 过滤，回表后再校验一次归属。任何一处写错都是数据泄露。
删掉之后，这一类风险彻底消失，功能没有任何损失。

### 商品：不需要语义检索

商品规模很小，且没有运行时写入接口——改价改描述都靠脚本，索引必然陈旧。
「杯子」匹配不上「马克杯」确实是词汇问题，但解法不是向量：

- 每次查询要付一次嵌入 API 往返（约 200ms + 费用），只为在 5 条数据里找
- 可能出现假阳性，比如「手机」因「手工」二字误命中
- 商品改名后索引不更新，召回直接失效

改为：精确匹配查不到时，返回**全部在售商品**让模型判断。5 条数据约
500 token，比一次 API 调用更便宜，且不会错。

商品规模到几百条时再说。那时也该先考虑中文分词，而不是向量。

### FAQ：唯一适合的

47 条且会持续增长，顾客说「退货运费谁出」与条款写「运费承担」之间的
词汇差异真实存在，语义检索的价值在这里成立。

## 实现变更

| 位置 | 变更 |
|---|---|
| `vector_store.product_document` | 删除 |
| `vector_store.work_order_document` | 删除 |
| `vector_store.rebuild_from_store` | 只索引 FAQ |
| `main.confirm_work_order` 的双写 | 删除 |
| `tools._semantic_products` | 删除 |
| `tools._resolve_source` | 删除，FAQ 回表内联 |
| `tools.lookup_product` | 查不到时返回全部在售商品 |
| `tools.search_knowledge` | 只查 FAQ，无需 visitor 参数 |
| `store.product_by_id` 等五个函数 | 删除，已无引用 |

## 内容来源原则

检索命中的内容**一律取自 MySQL 原文**，不使用向量库里存的拼接文本——
后者为检索优化过，可能截断或合并字段，不能作为回答依据。

相似度排序在应用层显式做（`sorted(..., reverse=True)`），不依赖向量库
返回顺序。

## 验收

1. 重建索引只产生 47 条（FAQ）
2. 「退货运费谁出」命中 P-RET-001 与 P-LOG-002，回答引用规则编号
3. 「我想买个杯子送人」由 `lookup_product` 返回全部在售商品，模型自行筛选
4. 工单查询走 `list_my_orders` / `lookup_work_order`，与向量无关
5. `uv run pytest` 全绿（81 项）

## 影响

- 工单不再进向量库 → 少一类私有数据泄露面
- 商品查询多一次全量返回 → 数据量小时可接受，规模上来后需重新评估
- 重建索引更快（47 vs 250 条）
