# ShopPilot 阶段四设计：工单可见化与前端确认

日期：2026-10-28
状态：已确认

## 意图

顾客反应「用户不知道有哪些工单」。前一版把建单决定交给模型、把工单信息藏在
聊天文本里，导致三个问题：

1. 顾客不知道系统里有哪些订单、哪些工单，只能靠记忆报订单号
2. 工单信息只存在于 AI 的措辞中，AI 说错顾客无从核对
3. 首单顾客永远建不了工单——校验要求订单已存在于库中，但新订单没有工单记录

这一版把**订单与工单变成界面上可见的对象**，把**写入权从模型收归给顾客点击**。

## 目标

1. 顾客能看到自己名下全部订单，无需记忆订单号
2. 顾客能看到自己名下全部工单及其状态
3. 建单由顾客在界面上点「确认提交」触发，AI 无法直接写入
4. 卡片与面板的数据一律来自数据库，不采信模型输出的文字
5. 首单顾客（无任何工单记录但有订单）可以正常建单

## 非目标

- 工单状态流转、结案、指派
- 工单内追加留言、附件
- 订单搜索、分页
- 实时推送状态变化

## 反目标

- 不允许 AI 输出的文本成为工单内容的来源
- 不允许顾客对不属于自己的订单建单
- 不允许同一订单同类型未完结工单重复

## 核心原则

**AI 是解说员，数据库是账本。** 界面上出现的每一个工单号、状态、内容，
都必须能追溯到数据库的某一行。AI 的措辞不构成凭据。

## 数据模型

### 新增 `orders`

```sql
orders(
  order_no     VARCHAR(32) PRIMARY KEY,
  visitor_id   VARCHAR(64),
  product_id   VARCHAR(32) NULL,
  quantity     INT,
  amount_cents INT,
  created_at   DATETIME(6)
)
```

订单是独立事实，不再从工单反推。归属校验改为查这张表，
因此「没有任何工单记录的新订单」也能正常建单。

### 新增 `work_order_drafts`

```sql
work_order_drafts(
  id, visitor_id, conversation_id, order_no, issue_type,
  description, created_at, expires_at
)
```

草稿是「已填好但未提交」的建单参数，存库而非留在前端内存，理由：
- 前端提交时只上送 `draft_id`，**内容不可篡改**
- 刷新页面后草稿仍在（30 分钟内）
- 草稿与工单物理分开，草稿不产生任何工单记录

## 两条建单路径

### A. 顾客主动（不经过 AI）

```
订单面板 → 点某笔订单「就此单提交工单」
        → 选问题类型 + 填描述 → 提交
        POST /api/work-orders/drafts → 得 draft_id
        POST /api/work-orders        → 写库
```

全程 AI 不参与，内容完全由顾客填写。

### B. AI 辅助起草

```
顾客描述问题 → AI 调 list_my_orders 定位订单
            → AI 调 draft_work_order 起草
            → 后端从工具入参建草稿，经 SSE 推 {"work_order_draft": ...}
            → 前端渲染确认卡片
            → 顾客点「确认提交」→ POST /api/work-orders → 写库
```

AI 能做的只有「起草」，写入永远由顾客的点击触发。AI 也无法在正文里
编造工单号——此时工单还不存在，prompt 明确禁止说「已提交」。

## 工具变更

| 工具 | 变化 |
|---|---|
| `list_my_orders` | 新增，无参数，列出本人订单及已有工单 |
| `draft_work_order` | 取代 `create_work_order`，只建草稿不写工单 |
| `lookup_work_order` | 不变 |
| `lookup_product` | 不变 |

`draft_work_order` 的工具描述中写明「本工具不会真正提交」「不要宣称已提交」，
并在返回值里再强调一次。

## 接口

| 接口 | 说明 |
|---|---|
| `GET /api/orders?visitor_id=` | 本人订单列表，附带每单已有关联工单 |
| `GET /api/work-orders?visitor_id=` | 本人工单列表 |
| `POST /api/work-orders/drafts` | 顾客主动提单时建草稿 |
| `POST /api/work-orders` | 凭 `draft_id` 确认提交 |

`POST /api/work-orders` 只接受 `draft_id` 与 `visitor_id`，**不接受任何内容字段**。
草稿内容从库里读，前端无法篡改。

## SSE 新增事件

```json
{"work_order_draft": {
   "draft_id": "drf-...",
   "order_no": "ORDER20260002",
   "issue_type": "运输破损",
   "description": "...",
   "product": "真空保温杯（粉色）",
   "expires_at": "..."
}}
```

由后端在 `draft_work_order` 工具成功返回后直接推送，内容取自工具的结构化入参
与数据库，**不经过模型的自然语言转述**。

## 前端

- 「我的工单」按钮改为双标签面板：**我的订单** / **我的工单**
- 订单项显示订单号、商品、数量、金额、下单时间、已有关联工单徽标，
  底部「就此单提交工单」内联表单
- 工单项显示工单号、状态徽标、类型、订单号、描述、涉及商品、更新时间
- 聊天中的确认卡片：字段逐行列出供核对，两个按钮「确认提交」「取消」
- 提交后卡片原地变为结果卡片（工单号 + 状态），可跳转面板

## 防幻觉措施汇总

| 措施 | 实现 |
|---|---|
| 卡片内容不采信模型文本 | 后端从工具入参建草稿，SSE 直推 |
| AI 无法直接写库 | 工具只建草稿，写库在确认接口 |
| 顾客可核对 | 卡片与面板展示库中原文，含订单号与商品 |
| 状态不篡改 | 状态取自 `work_orders.status`，前端只做徽标渲染 |
| 重复提单 | 草稿接口与确认接口双重去重 |

## 已知残留风险

prompt 禁止 AI 编造工单号，但没有代码层校验正文中的 `WO` 号。当前
AI 无法取得工单号（工具不返回、草稿不生成号），因此实际风险很低；
若将来加入「查工单号」能力，需要补正文回查。

## 验收标准

1. 打开面板可见本人全部订单，含从未提过工单的订单
2. 对从未提过工单的订单可直接建单成功
3. AI 起草后聊天中出现确认卡片，AI 正文不说「已提交」
4. 点确认提交后卡片变为工单号 + 状态
5. 同订单同类型重复提交被拒，提示既有工单号
6. 同订单不同类型可正常建单
7. 换访客 id 看不到他人订单与工单
8. `uv run pytest` 全绿

## 留给构建者的决定

- 面板标签的默认页签（当前为「我的订单」）
- 草稿 30 分钟有效期的具体时长
